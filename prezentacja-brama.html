Problem

Kod z LLM zwykle „działa”. To jest problem.

manager

Co się psuje w organizacji

Zespół dostaje więcej PR-ów niż da się przeczytać. Recenzent klika „approve”, bo testy są zielone i diff „wygląda na kod”. Defekt wychodzi na produkcji albo w kolejnym sprincie — i nikt nie umie powiedzieć, który model go wpuścił.

Brama nie zastępuje człowieka. Zastępuje złudzenie, że zielone CI = bezpieczny merge.

inżynier

Dlaczego pipeline tego nie łapie

Klasyczny CI zakłada, że testy, lockfile i opis PR są niezależnym dowodem. Przy agencie wszystkie pochodzą od tego samego autora co kod. Coverage rośnie. Testy asertują to, co kod robi. CI instaluje pakiet, który agent wymyślił.

Trzeba weryfikować artefakty, którym normalnie ufamy.

Nie-cel: zastąpić code review. Cel: zablokować to, co maszyna łapie pewniej, i dać człowiekowi raport zamiast surowego diffa.

Teoria · aksjomat

Jedno założenie, na którym stoi reszta

Testy, lockfile, konfiguracja i opis PR pochodzą od tego samego autora co kod — więc żadnego z nich nie wolno traktować jako niezależnego dowodu.

Skutek dla testów

Zielony test nic nie znaczy, dopóki nie udowodnimy, że pada na kodzie sprzed zmiany. Inaczej test ozdabia implementację.

Skutek dla zależności

Manifest nie jest źródłem prawdy. Pakiet musi istnieć w rejestrze, nie być młody i nie być homoglifem popularnej nazwy.

Skutek dla polityki

Kryteria oceny leżą w ocenianym repo i agent nie może ich „naprawić”. CODEOWNERS + branch protection to granica bezpieczeństwa, nie formalność.

Stąd kolejność bramek: najtańsze i najbardziej deterministyczne najpierw. Recenzent LLM (G4) jest drogi i niedeterministyczny — nie wolno nim przykrywać dziur, które tanie bramki już umieją strzec.

Co to znaczy dla procesu

Faza 1 (G0+G1+G3) daje ok. 60% wartości przy ~20% kosztu. G2 jest najtrudniejsza i najbardziej wartościowa — tu ginie „zielone, ale puste”. G4 włączamy do blokowania dopiero przy precyzji >80% na kalibracji. Pełny łańcuch to ~3 miesiące; pierwsza wartość po ~3 tygodniach.

inżynier

Co jest w silniku dziś

Zbudowane: G0, G1 (w tym complexity), G2 (Python + C#), G3. Niezbudowane: mutacje, flaky, kontrakty, IaC, licencje, G4 panel, G5 jako polityka człowieka poza human_review_required_when, G6 checklist wdrożeniowy.

Decyzja

Trzy werdykty, zero „score 82/100”

PASS

Bramki zielone, dowody zebrane. Kod wyjścia 0.

PASS-WITH-REVIEW

Nie blokuję, ale człowiek ma zerknąć — i raport mówi gdzie. Kod 0 (albo 2 przy --fail-on review).

BLOCK

Twardy stop z uzasadnieniem, scenariuszem awarii i fingerprintem. Kod 1.

Filozofia: fail-closed

  • brak narzędzia → error, nie cichy pass
  • brak dowodu → on_gate_error: review, nigdy fałszywie zielony Check Run
  • raport jawnie wymienia not_checked
  • każde znalezisko musi mieć scenariusz awarii — bez niego obiekt się nie tworzy
  • fingerprint bez numeru linii — wyciszenie przeżywa rebase

Architektura · dla inżynierów

Core nie importuje packów. Packi się dorejestrują.

Dwupoziomowe entry points (importlib.metadata). Polityka referencuje gate ID jako string — dlatego G1.static zostaje jedną bramką niezależnie od liczby języków w PR.

Użycie · start w 5 krokach

Scenariusz A — ręcznie, na gałęzi agenta

1. Zainstaluj core + packi języków, które naprawdę są w repo (z GitHuba, nie PyPI).

2. Doinstaluj narzędzia bramek: ruff/mypy, gitleaks, ewentualnie tsc/eslint, .NET SDK.

3. Upewnij się, że testy ocenianego projektu w ogóle się zbierają (pytest --collect-only / dotnet test).

4. Skopiuj policy/gates.yaml i exceptions.yaml do ocenianego repo. Chroń policy/ przez CODEOWNERS.

5. Stojąc na gałęzi agenta:

gatekeeper policy lint --policy policy/gates.yaml
gatekeeper run --repo . --base origin/main
manager

Ile to rusza zespół

Jednorazowo: instalacja, kopia polityki, wpis w CI. Potem zero nowego rytuału — brama odpala się na PR.

Pierwszy tydzień: tryb ostrzeżeń (szablon ma warn_only na G1.static / G2 / G3.sast / G3.sca). Potem zdejmij warn_only, zanim Check Run stanie się required.

Dopóki warn_only zostaje, brama komentuje, nie chroni. Naprawdę blokuje wtedy: sekret, nieistniejący pakiet, typosquat, zbyt duży diff.

Użycie · raport i pętla

Co robić z werdyktem

Czytanie raportu

  • każde znalezisko = plik + fakt + bramka + fingerprint + scenariusz awarii
  • przebieg w nagłówku → gatekeeper incident
  • fingerprint → gatekeeper verdict … --false-positive
  • bramka w warn-only failuje, ale nie blokuje merge

Pętla z agentem

Nie poprawiaj ręcznie. Wklej raport agentowi jako zadanie. Maks. 2–3 rundy, potem człowiek — inaczej pętla produkuje obejścia.

Fałszywy alarm: nie wyłączaj reguły. Oznacz verdict + wyjątek w exceptions.yaml z właścicielem i datą wygaśnięcia.

Ściąga CLI

gatekeeper run --base main
gatekeeper run --gate G1.deps
gatekeeper run --base main --fail-on review

Użycie · polityka i CI

Kryteria oceny są kodem w ocenianym repo

Szablon: core/policy/gates.yaml. Blocking to fakty, nie „score”. Progi: diff, coverage, complexity, SAST, SCA. Ścieżki wrażliwe (auth/, payments/, migrations/, policy/) wymuszają review.

blocking:
  - secrets.found_in_diff
  - deps.unknown_package
  - deps.typosquat_suspect
  - tests.pass_on_pre_change_code

warn_only:          # zdejmij przed required check
  - G1.static
  - G2.cross_verify
  - G3.sast
  - G3.sca
CI

Szablon workflow: python/.github/workflows/gatekeeper.yml (uniwersalny, mimo katalogu). Check Run z werdyktem. Docs-only idzie ścieżką szybką, sekrety i tak.

Granica: agent bez uprawnień do policy/ i .github/. Placeholder @wlasciciel-bramy nic nie egzekwuje — trzeba prawdziwych owners i branch protection.

Uczciwy stan · decyzja

Co wolno obiecać organizacji dziś

Gotowe do adopcji

  • halucynowane pakiety i typosquat (PyPI/npm/NuGet)
  • limity rozmiaru PR i sekrety także w testach
  • static/SAST na zmienionych liniach, 3 języki
  • dowód testów dla Pythona i C#
  • polityka jako YAML, ślad w SQLite, kalibracja core 5/5

Nie obiecuj jeszcze

  • że domyślny szablon blokuje static/SAST/SCA/G2 — nie blokuje
  • dowodu behawioralnego dla TypeScriptu
  • recenzenta LLM (G4), deploy checklist (G6)
  • twardej izolacji poza Linuxem / kontenerem
  • instalacji z PyPI i wypchniętego CI (token bez scope workflow)

Następny krok nie jest nową bramką. Jest zdjęciem warn_only i naprawą CODEOWNERS — potem G2 dla TS, potem dopiero G4.
