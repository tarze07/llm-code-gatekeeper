potrzeba03 / 15

Kod z LLM zwykle „działa”.
I to jest problem.

Standardowy CI odpowiada na pytanie „czy kod nie działa?” — łapie błędy kompilacji i czerwone testy. Agent produkuje kod, który przechodzi oba te próby, a mimo to wycieka na produkcję coś innego:

  • halucynowany pakiet, którego nie ma w rejestrze — albo typosquat,
  • test-atrapa: zielony, ale asertuje to, co kod i tak robi,
  • sekrety w fixture’ach i diff poza zakresem zlecenia.

Klasyyczny pipeline zakłada, że testy, lockfile i opis PR są niezależnym dowodem. Przy agencie — nie są.

Co dziś widzi recenzent

  • ✅ testy zielone
  • ✅ coverage rośnie
  • ✅ zależności zainstalowane z lockfile’a
  • ⚠️ diff 900 linii w 30 plikach — „jutro doczytam”

…a każdy z tych zielonych punktów napisał ten sam autor co kod. Recenzent klika approve, bo artefakty wyglądają na niezależne — i nie sposób potem ustalić, który model wpuścił defekt.

Nie-cel systemu: zastąpić code review. Cel: zablokować klasy błędów, które maszyna łapie taniej i pewniej, a człowiekowi dać raport zamiast surowego diffa.

wiedza teoretyczna · aksjomat05 / 15

Jedno założenie, na którym stoi cały system

Testy, lockfile, konfiguracja i opis PR pochodzą od tego samego autora co kod — więc żadnego z nich nie wolno traktować jako niezależnego dowodu.

Skutek dla testów

Zielony test nic nie znaczy, dopóki nie udowodnimy, że pada na kodzie sprzed zmiany. Inaczej tylko ozdabia implementację.

Skutek dla zależności

Manifest nie jest źródłem prawdy. Pakiet musi istnieć w rejestrze, nie być zbyt młody i nie być homoglifem popularnej nazwy.

Skutek dla polityki

Kryteria oceny leżą w ocenianym repo i agent nie może ich „naprawić”. CODEOWNERS + branch protection to granica bezpieczeństwa, nie formalność.

Stąd zasada kolejności bramek: najtańsze i najbardziej deterministyczne najpierw. Recenzent LLM (G4) jest drogi i niedeterministyczny — nie wolno nim przykrywać dziur, które tanie bramki już umieją strzec.

model decyzji07 / 15

Trzy werdykty i filozofia fail-closed

PASS

Zielone światło

Bramki zielone, dowody zebrane. Kod wyjścia 0.

PASS-WITH-REVIEW

Człowiek zerka

Nie blokuję, ale raport mówi gdzie patrzeć. Kod 0 (lub 2 z --fail-on review).

BLOCK

Twardy stop

Uzasadnienie, scenariusz awarii, fingerprint. Kod wyjścia 1.

Brak dowodu ≠ pass

  • brak narzędzia → error, nie cichy pass
  • błąd bramki → on_gate_error: review
  • raport jawnie wymienia not_checked — brama przyznaje się, czego nie sprawdziła

Dowód w każdym znalezisku

  • Finding bez scenariusza awarii nie potrafi powstać (walidacja w konstruktorze)
  • fingerprint bez numeru linii — wyciszenia przeżywają rebase
  • przebiegi lądują w SQLite: incident, verdict, metrics
jak przygotowano rozwiązanie08 / 15

Siedem kroków: od dokumentu do zweryfikowanego systemu

  1. Rozpoznanie. Taksonomia defektów kodu z agenta i model zagrożeń (core/PLAN.md) — wybór 7 klas deterministycznych.
  2. Model decyzji. Fakty, progi, werdykty; polityka jako YAML bez eval; wyjątki z właścicielem i datą wygaśnięcia.
  3. Kontrakty pluginów. Protokoły StaticChecker, TestToolchain, EcosystemProvider, SemgrepRulePack — dwa poziomy entry points.
  4. Silnik. Orchestrator (fale wg grafu zależności, budżety, ścieżka docs-only), sandbox procesów, raport do PR, ślad w SQLite.
  5. Packi językowe. ruff/mypy · tsc/eslint · dotnet build + helper Roslyn gatekeeper-cs-helper.
  6. Kalibracja. Fixture’y celowo zepsutych PR-ów: sekret, halucynowany pakiet, za duży diff, test bez dowodu — stała regresja samej bramy.
  7. Weryfikacja. Osobno każde repo (pytest, mypy --strict, semgrep --test, calibrate) i mieszany stos: 4 pakiety w jednym venv, diff Python+TS+C# jednym gatekeeper run.

Rozstrzygnięcia projektowe

  • Monorepo, nie 4 osobne repo — wspólny core + cienkie packi w jednym repo (`#subdirectory=`), historia git zachowana przez git filter-repo przy scaleniu
  • PyPI/npm/NuGet zostają w core: manifest+rejestr+typosquat+SCA to infrastruktura, nie kompilatory
  • G1.complexity jako osobny gate ID, nie wpinka do ruffa C901 — własna dźwignia w polityce
  • rollout: pierwszy tydzień warn_only, potem zdjęcie ostrzegania przed ustawieniem required check

Uczciwość jako cecha systemu

Brak narzędzia czy brak dowodu to w raporcie skipped + not_checked, nie udawany pass. G2 dla TS odpala się tylko gdy w package.json jest vitest albo jest — repo z samym tape dostanie skipped, nie zielony kwiatek. Toolchain TS jako jedyny deklaruje dwa języki (TS i JS jednym przebiegiem runnera).

Sandbox wykonania

Brama uruchamia kod z PR-a. Jeden punkt subprocess: scrub zmiennych TOKEN/SECRET, unshare --net, RLIMIT pamięci/czasu, allowlista env. Linux-first; twarda izolacja kontenerowa — otwarty dług.

najważniejsza bramka12 / 15

G2.cross_verify — test, który musi paść na starym kodzie

1

Worktree ze starym kodem

Brama tworzy checkout base_sha — wersji sprzed zmiany z PR-a.

2

Overlay tylko testów

Na stary kod kopiowane są tylko nowe/zmienione pliki testowe. Produkcja nie może wyciec do bazy.

3

Uruchom nowe testy

Jeśli test nowej funkcjonalności przechodzi na starym kodzie — nie dowodzi zmiany → finding.

Test sanity (AST / ESTree / Roslyn lint)

Test bez asercji · asercja na stałą (Assert.Equal(1,1)) · echo mocka (Moq, vi.fn/jest.fn zwraca to, co test sam ustawił) · sam is not None / toBeDefined · połknięty wyjątek. Te same pięć rule_id w trzech językach. Markery characterization/test_backfill z licznikiem nadużyć.

Diff coverage

Pokrycie różnicowe, branch-aware (coverage.py · vitest/jest --coverage → Cobertura · coverlet + diff-cover): liczy się tylko to, co zmienił PR — ≥ 80%. Globalny percentage łatwo oszukać, diffowy nie.

Detale: weryfikacja izolacji (Python: wykrycie pip install -e; TS: node_modules z dowiązaniem do repo — npm link/workspaces → IsolationBroken), rozróżnienie failed od error (błąd kompilacji na starym kodzie to słabszy dowód — liczy się osobno). TS celowo na ESTree, nie TS Compiler API: od TypeScript 7 pakiet typescript nie eksponuje już parsera w JS.

  git+…tarze07/llm-code-gatekeeper.git#subdirectory=ts"
# analogicznie: llm-code-gatekeeper-csharp

2 · Uruchomienie bramy na gałęzi agenta

gatekeeper policy lint --policy policy/gates.yaml
gatekeeper run --repo . --base origin/main

3 · Narzędzia projektów ocenianych

StosPoza pipem bramy
Pythonruff, mypy, binarka gitleaks

4 · Polityka

Skopiuj gates.yaml / scope_map.yaml / exceptions.yaml (kopia startowa: core/policy/) do ocenianego repo. Chroń policy/ prawdziwymi CODEOWNERS + branch protection.

Mieszany stos? Instalujesz core + tyle packów, ile języków w repo. gatekeeper run obsłuży Python+TS+C# w jednym diffie, jednym raportem.

użycie · raport, pętla, CI14 / 15

Co robić z werdyktem

Czytanie wyniku

  • finding = plik + fakt + bramka + fingerprint + scenariusz awarii
  • każdy przebieg zostaje w SQLite → gatekeeper incident <run-id>
  • fałszywy alarm? nie wyłączaj reguły — oznacz gatekeeper verdict <fp> --false-positive i wpisz wyjątek z właścicielem i datą wygaśnięcia
  • skuteczność bramy: gatekeeper metrics --days 30

Pętla z agentem

Raport BLOCK wklej agentowi jako zadanie naprawcze. Maks. 2–3 rundy, potem człowiek — dłuższa pętla produkuje obejścia zamiast poprawek.

gatekeeper run --base main
gatekeeper run --gate G1.deps        # jedna bramka
gatekeeper run --base main --fail-on review
gatekeeper policy facts              # dozwolone fakty
gatekeeper calibrate                 # naprawcze PR-y vs polityka
gatekeeper verdict <fp> --false-positive --note "…"
gatekeeper metrics --days 30

Uwaga wdrożeniowa

Szablon startowy ma warn_only na G1.static, G3.sast, G3.sca i G2.* — do pierwszego tygodnia obserwacji. Dopóki zostaje, brama komentuje, nie chroni: naprawdę blokuje tylko sekrety, nieistniejący pakiet, typosquat i za duży diff. Zdejmij warn_only, zanim Check Run stanie się required. Gotowy workflow CI: .github/workflows/gatekeeper.yml.

uczciwy stan i następne kroki15 / 15

Co wolno obiecać organizacji dziś

GOTOWE DO ADOPCJI
  • halucynowane pakiety i typosquat (PyPI/npm/NuGet)
  • sekrety także w testach; limity zakresu i rozmiaru diffa
  • statyka, złożoność i reguły „nigdy” w 3 językach
  • dowód testów (cross-verify, sanity, diff coverage) dla Pythona, TS/JS i C#
  • polityka jako YAML, kalibracja, ślad w SQLite, metryki
NIE OBIECUJ JESZCZE
  • że domyślny szablon blokuje static/SAST/SCA/G2 — częściowo tylko ostrzega
  • G2 w repo TS, którego runnerem nie jest vitest/jest (brak detekcji → skipped)
  • recenzenta LLM (G4) i checklisty wdrożeniowej (G6)
  • twardej izolacji poza Linuksem; pakietów na PyPI; wypchniętego CI (token bez scope workflow)

Następny krok nie jest nową bramką. Jest zdjęciem warn_only, naprawą CODEOWNERS i domknięciem fail-open — potem dopiero G4.
