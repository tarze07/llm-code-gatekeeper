Problem: kod z LLM zwykle „działa” — i to jest problem

Klasyczny CI łapie „kod nie działa”. Kod z agentów LLM zwykle działa — a i tak wycieka do produkcji przez:

halucynowane pakiety

import istnieje tylko w wyobraźni modelu — albo to typosquat / slopsquat

testy-atrapy

nowe testy niczego nie dowodzą: brak asercji, asercja na stałą, echo mocka

sekrety w fixture'ach

token API wpięty „na próbę” w pliku testowym

diff poza zakresem

agent „przy okazji” przepisuje połowę repo

Założenie projektowe (prawdziwe)

Testy, lockfile, konfiguracja i opis PR pochodzą od tego samego autora co kod — więc żadnego z nich nie wolno traktować jako niezależnego dowodu.

Jak brama decyduje

Jedno polecenie na cały PR — niezależnie od liczby języków w diffie:

gatekeeper run --repo /ścieżka/do/repo --base origin/main

PASS

wszystkie bramki zielone, dowody zebrane

PASS-WITH-REVIEW

przechodzi, ale wymaga człowieka przy merge

BLOCK

twarde stop z uzasadnieniem i fingerprintami

Filozofia: fail-closed, nie fail-open

  • brak narzędzia → error, nie cichy pass
  • brak dowodu → on_gate_error: review, nigdy zielony Check Run
  • raport jawnie wymienia not_checked
  • ślad przebiegów w SQLite, fingerprint bez numeru linii — wyciszenia przeżywają rebase

Architektura: 4 repozytoria, nie 3

Jeden monolit Pythona podzielono git filter-repo (zachowana historia) na wspólny rdzeń i trzy cienkie packi językowe:

core

silnik, CLI, 11 bramek, PyPI/npm/NuGet
gatekeeper_core

python

ruff / mypy, testy przez ast, SAST Pythona
gatekeeper_python

ts

tsc / eslint, SAST TS/JS
gatekeeper_ts

csharp

dotnet build, helper Roslyn, SAST C#
gatekeeper_csharp

Dlaczego PyPI/npm/NuGet zostały w core?

Manifest + rejestr + typosquat + SCA nie mają logiki specyficznej dla kompilatora — to czysta infrastruktura bramek G1.deps/G3.sca. Rozbicie na 3 kopie tylko duplikowałoby parsery manifestów.

Najważniejsza bramka: G2.cross_verify

Nowe testy z PR-a lecą na worktree ze starym kodem — test, który niczego nie dowodzi, nie ma prawa przejść. Overlay tylko plików testowych, detekcja pip install -e (izolacja zepsuta → error), markery characterization/test_backfill z licznikiem nadużyć.

Bezpieczeństwo: brama wykonuje kod z PR-a

Jedyny punkt subprocess (runner.py) to świadoma granica bezpieczeństwa:

Izolacja procesu

  • scrub zmiennych TOKEN/SECRET/PASSWORD
  • unshare --net — sieć off bez roota
  • RLIMIT pamięci i czasu, zabijanie grupy procesów
  • keep_env jako allowlista, nie denylista

Uczciwość raportu

  • describe_isolation() — raport mówi, jaka izolacja faktycznie była
  • sekrety redagowane w findings (osobny test)
  • overlay G2 nie kopiuje produkcji do base worktree
  • only_changed_lines — wdrożenie na starym repo nie zabija projektu

Nierozwiązane: brak ContainerSandbox (Linux-only), macOS/Windows bez netns, require_isolation: false jako default.

Weryfikacja (stan po Fazie 1)

  • Każde repo z osobna: ruff + mypy --strict + pytest + policy lint + calibrate — zielone
  • Core dodatkowo: semgrep --test + 5/5 przypadków kalibracyjnych (PyPI i npm), 62 testy
  • Reguły SAST per język: 6/4/4 semgrep --test (python / ts / csharp)
  • Wszystkie 4 naraz: spójne 11 gate ID; mieszany diff Python+TS+C# jednym gatekeeper run → PASS, każdy checker realnie odpalony jednym wywołaniem
  • C#: nowy helper Roslyn gatekeeper-cs-helper — G2.* istnieje dziś dla Pythona i C#; TS/JS świadomie odłożone (brak toolchainu = skipped, nie błąd)

Review — znaleziska krytyczne (P0)

P0 — domyślna polityka prawie nic nie blokuje

G1.static, G3.sast, G3.sca, G2.* są w warn_only. Naprawdę blokuje tylko: sekret, nieistniejący pakiet, typosquat, diff > 400 linii / 15 plików. Zespół może dostać zielony Check Run i uznać, że brama „chroni”.

P0 — CODEOWNERS to atrapa

/policy/ @wlasciciel-bramy — placeholder, nie handle. Granica „agent nie zmienia kryteriów oceny” nie istnieje dopóki consuming repo nie włączy branch protection.

Największe ryzyko

„Nie budować G4, dopóki domyślna polityka nie blokuje G1/G3. Inaczej drogi, niedeterministyczny recenzent przykryje dziury, których tanie bramki już umieją strzec.”

Review — pozostałe znaleziska (P1 / P2)

P1

  • allow_packages normalizuje zawsze jako PyPI → martwa dla npm/NuGet
  • eslint/tsc fail-open przy śmieciowym outputcie (JSONDecodeError → [])
  • G1.static przerywa na pierwszym errorze checkera
  • sandbox bez kontenera, Linux-only

P2

  • podwójna rejestracja bramek (@register + entry points)
  • dryf szablonów gates.yaml między 4 repo
  • brak górnego boundu zależności core>=0.1.0
  • homoglify typosquatu niepełne; CI nie wypchnięte (token bez scope workflow)

Jakość kodu — mocne strony

Python 3.12, mypy --strict, ruff; komentarze tłumaczą dlaczego, nie co; testy na zachowanie, nie na mocki (golden files semgrep/gitleaks/pip-audit); kalibracja jako regresja samej bramy.

Werdykt review

Jako fundament badawczo-inżynierski

7.5 / 10

„Nie jest to kolejny wrapper na Semgrep. Jest model defektów specyficznych dla agentów i silnik, który ten model egzekwuje uczciwie: brak dowodu ≠ pass, luki są nazwane, polityka jest kodem.”

Jako gotowy gate w CI

5 / 10

Domyślnie nie blokuje static/SAST/SCA/testów; TS nie ma dowodu behawioralnego; ochrona policy/ papierowa; izolacja procesów nie twarda.

Najlepsza następna kroka — wg recenzenta

Nie nowa bramka, tylko włączenie tych, które już są, plus naprawa P0/P1.

Droga dalej

  • naprawić allow_packages — normalizacja per ekosystem
  • JSONDecodeError → [] zamienić na ToolFailed (fail-closed)
  • CODEOWNERS: prawdziwe handle albo usunąć plik
  • pin core>=0.1.0,<0.2, wypchnąć CI (gh auth refresh -s workflow)
