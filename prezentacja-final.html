llm-code-gatekeeper · prezentacja projektowa

Czy kod z agenta może iść na produkcję?

Automatyczna brama jakości dla zmian tworzonych przez agentów LLM. Od modelu zagrożeń, przez architekturę i implementację, aż po użycie w repozytorium i CI.

potrzeba → teoria → rozwiązanie → użycie

Potrzeba

Zielone CI nie oznacza, że zmiana jest bezpieczna i wartościowa.

Rozwiązanie

01 · Potrzeba

Klasyczny CI odpowiada na zbyt wąskie pytanie

CI sprawdza głównie: „czy kod się buduje i czy testy przechodzą?”. Brama pyta: „czy ta zmiana może iść na produkcję?”.

Dlaczego kod z LLM jest inny

  • Agent tworzy jednocześnie kod, testy, konfigurację i opis PR.
  • Te artefakty nie są niezależnym dowodem — mogą wzajemnie potwierdzać ten sam błąd.
  • Kod często działa na happy path, ale ukrywa ryzyka poza nim.
problem organizacyjny

Więcej zmian, mniej czasu na recenzję

Recenzent widzi zielony pipeline i duży diff. Trudno ustalić, co naprawdę zostało sprawdzone, a co tylko przeszło przez automaty.

Cel: maszyna blokuje powtarzalne klasy błędów, a człowiek dostaje raport wskazujący miejsca wymagające decyzji.

02 · Wiedza teoretyczna

Założenie, które definiuje projekt

Testy, lockfile, konfiguracja i opis PR pochodzą od tego samego autora co kod. Żadnego z nich nie traktujemy automatycznie jako niezależnego dowodu.

Dowód testu

Nowy test powinien polec na kodzie sprzed zmiany. Jeśli przechodzi — może nie dowodzić nowej funkcji.

Dowód zależności

Pakiet musi istnieć w oficjalnym rejestrze, mieć odpowiedni wiek i nie przypominać popularnej nazwy.

Dowód polityki

Kryteriów oceny nie może zmieniać agent. policy/, CI i CODEOWNERS wymagają ochrony.

Zasada kolejności

Najpierw kontrole tanie i deterministyczne. Dopiero po nich kosztowny i niedeterministyczny review LLM.

Dlaczego etapami

02 · Decyzja

Wynik jest jawny, nie sprowadzony do „score 82/100”

PASS

Bramki zielone, dowody zebrane. Kod wyjścia 0.

PASS-WITH-REVIEW

Zmiana nie jest zablokowana, ale raport wskazuje obowiązkowy obszar decyzji człowieka.

BLOCK

Twardy stop z uzasadnieniem, scenariuszem awarii i fingerprintem.

Fail-closed w praktyce

  • brak narzędzia → error, nie cichy pass
  • brak dowodu → on_gate_error: review
  • raport pokazuje not_checked
  • fingerprint nie zawiera numeru linii, więc przeżywa rebase
03 · Przygotowanie rozwiązania

Najpierw plan i kontrakty, potem implementacja

Kroki wykonane / przewidziane

  1. Opisanie klas defektów charakterystycznych dla pracy z agentem.
  2. Zdefiniowanie łańcucha G0–G6, faktów, progów i werdyktów.
  3. Rozdzielenie silnika od implementacji językowych.
  4. Zaprojektowanie kontraktów pluginów i agregatorów.
  5. Zbudowanie fixture’ów kalibracyjnych: czysta zmiana, duży diff, sekret, halucynowana zależność.
  6. Testowanie jednostkowe, integracyjne, SAST i scenariuszami end-to-end.

Polityka jako kod

YAML określa fakty blokujące, progi, wyjątki, wymagany review i zachowanie przy błędzie.

blocking:
  - secrets.found_in_diff
  - deps.unknown_package
  - deps.typosquat_suspect
thresholds:
  diff.effective_lines:
    max: 400
  complexity.max:
    max: 10

Wyjątek ma właściciela, powód i datę wygaśnięcia.

03 · Architektura

4 repozytoria: wspólny core + packi językowe

core

silnik, CLI, polityka, orchestrator, 11 bramek jako dispatch, PyPI/npm/NuGet

gatekeeper_core

python

ruff, mypy, AST, pytest, coverage, SAST

gatekeeper_python

ts / js

tsc, eslint, complexity i SAST

gatekeeper_ts

csharp

dotnet build, Roslyn helper, xUnit, SAST

gatekeeper_csharp

Dlaczego nie duplikować logiki

Manifesty, rejestry, typosquat i SCA są wspólne dla ekosystemów. Zostają w core. Pack dostarcza tylko checker, toolchain testów i reguły właściwe dla języka.

Jeden gatekeeper run obsługuje mieszany diff bez importowania packów „na sztywno”.

04 · Najważniejsza technika

G2.cross_verify sprawdza, czy test naprawdę dowodzi zmiany

1

Stary kod

Utwórz worktree z base_sha, czyli wersją sprzed zmiany.

2

Overlay testów

Skopiuj do starego worktree tylko nowe lub zmienione pliki testowe.

3

Uruchom

Jeśli nowy test przechodzi na starym kodzie, nie dowodzi nowej funkcji.

Kontrole jakości testu

AST/Roslyn wykrywa brak asercji, asercję na stałą, echo mocka i połknięty wyjątek. Coverage jest branch-aware i dotyczy diffa, nie całego repo.

04 · Bezpieczeństwo wykonania

Brama wykonuje kod z PR-a, więc raportuje granice izolacji

Obecne zabezpieczenia

  • scrub zmiennych TOKEN, SECRET, PASSWORD
  • unshare --net bez roota
  • limity pamięci i czasu, zabijanie grup procesów
  • allowlista środowiska i jawny opis izolacji

Ograniczenia

  • Linux-first; brak gotowego ContainerSandbox
  • poza Linuxem izolacja sieci może być słabsza
  • require_isolation: false jest domyślnie wygodne, ale nie idealne

To jest ryzyko operacyjne do zamknięcia przed użyciem z wrażliwymi tokenami CI.

05 · Użycie

Start na ocenianym repozytorium

1. Instalacja

pip install "llm-code-gatekeeper-core @ git+https://github.com/tarze07/llm-code-gatekeeper-core.git"
pip install "llm-code-gatekeeper-python @ git+https://github.com/tarze07/llm-code-gatekeeper-python.git"
# analogicznie: -ts i -csharp

2. Narzędzia językowe

Python: ruff, mypy, gitleaks. TS: tsc, eslint. C#: .NET SDK 8+ i gatekeeper-cs-helper.

3. Polityka w repo

Skopiuj policy/gates.yaml, scope_map.yaml i exceptions.yaml do ocenianego repo. Chroń policy/ i CI przez prawdziwych CODEOWNERS oraz branch protection.

4. Walidacja polityki

gatekeeper policy lint --policy policy/gates.yaml
05 · Użycie

Jedno polecenie na cały PR

gatekeeper run --repo /ścieżka/do/ocenianego/repo --base origin/main

Warianty

gatekeeper run --base main
gatekeeper run --gate G1.deps
gatekeeper run --base main --fail-on review

Diagnostyka

gatekeeper policy facts
gatekeeper calibrate
gatekeeper metrics --days 30

Decyzje

gatekeeper verdict <fingerprint> \
  --false-positive

gatekeeper incident <run-id>

Kody wyjścia: 0 = PASS, 1 = BLOCK, 2 = REVIEW przy --fail-on review, 3 = błąd użycia.

05 · Użycie w procesie

Raport staje się pętlą naprawczą, nie kolejnym szumem

Gdy jest BLOCK

  1. Przeczytaj finding: bramka, plik, fakt, fingerprint, scenariusz awarii.
  2. Przekaż raport agentowi jako konkretne zadanie naprawcze.
  3. Uruchom ponownie maksymalnie 2–3 iteracje.
  4. Jeśli problem jest zasadny, popraw kod; jeśli fałszywy, użyj jawnego verdictu i wyjątku z datą.

Gdy jest REVIEW

Człowiek dostaje wskazany obszar: auth, payments, migrations, infra, policy, nową zależność albo brak dowodu.

CI

Workflow uruchamia bramę na każdym PR i publikuje jeden aktualizowany Check Run / komentarz.

Pierwszy tydzień można prowadzić w warn_only. Przed oznaczeniem Check Run jako required trzeba zdjąć ostrzeganie z bramek, które mają realnie chronić.
06 · Wynik i dalsze kroki

Co można obiecać dziś, a czego jeszcze nie

Gotowe do adopcji

  • sekrety także w testach i fixture’ach
  • halucynowane pakiety i typosquat
  • limity zakresu i rozmiaru diffa
  • statyka, complexity i SAST w trzech packach
  • dowód testów dla Pythona i C#
  • polityka YAML, kalibracja, SQLite, metryki

Nie obiecuj jeszcze

  • że domyślny szablon blokuje każdą bramkę — część jest warn_only
  • dowodu behawioralnego dla TS/JS
  • panelu review LLM G4 i checklisty deploy G6
  • twardej izolacji kontenerowej na wszystkich systemach
  • publikacji pakietów na PyPI / pełnego CI na GitHubie

Najbliższy krok: włączyć egzekwowanie istniejących bramek, naprawić CODEOWNERS i fail-open, a dopiero potem rozwijać G2 dla TS i G4.
